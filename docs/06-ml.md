# 06 — ML readiness

Two things are genuinely worth doing now, while M1–M2 are being built anyway, because retrofitting
either one later means touching the engine, the bots, the protocol, and every stored record at
once: the **action encoding** and **persisting `GameRecord`** for finished games. Everything else
in this space is deferred — see §3 for why, including why "just start recording now" (an earlier
draft's advice) turned out not to help.

## 1. Action encoding

A fixed, flat, complete discrete space — every legal action maps to exactly one id, and back:

```
[  0 ..  33]  DISCARD          tile_type t
[ 34 ..  67]  CONCEALED_KONG   tile_type t      (暗槓)
[ 68 .. 101]  ADDED_KONG       tile_type t      (加槓)
        102   PASS                              (decline a claim — and decline a win)
        103   CHOW_LOW         claimed tile is lowest  → use t+1, t+2
        104   CHOW_MIDDLE      claimed tile is middle  → use t-1, t+1
        105   CHOW_HIGH        claimed tile is highest → use t-2, t-1
        106   PUNG
        107   KONG                              (exposed, from a discard)
        108   WIN                               (self-draw or on a discard)
                                                 N_ACTIONS = 109
```

- **Chow is relative** (low/middle/high) — the claimed tile is known from context. Same
  convention as Suphx/Mortal.
- **Kongs are tile-indexed** because you can hold several options at once on your turn.
- **`PASS` covers declining a win**, a real strategic choice under `min_faan`.
- Flower reveal is not an action — it's forced and the engine handles it.
- **`DISCARD` / `CONCEALED_KONG` / `ADDED_KONG` are indexed by `tile_type` (0–33), not physical
  `tile_id`.** This is deliberate, and it has a consequence you need to design around rather than
  discover in a failing test: the protocol's `discard {tile_id}` message and the client's
  animation need physical tile identity (four physical 5s are not interchangeable on screen), but
  the *action space* only ever needs to know which type left the hand — duplicate tiles of the
  same type are fungible to the engine. So `Intent` at the action-space boundary is
  **type-level only** (`tile_type`, never `tile_id`). When the engine applies a type-level
  discard, it removes a physical tile of that type from the hand by a fixed, deterministic rule
  (lowest remaining `tile_id` of that type), and the resulting event carries the physical
  `tile_id` the client animates. The *human* client's WS message still names a physical
  `tile_id`, so a click maps to the right sprite — the server translates that to `tile_type`
  before it ever touches `action_id`/`decode_action`. Bots never see or choose physical `tile_id`
  at all; they only ever produce type-level intents.

Two pure functions in `mahjong_core`, plus one property test — no numpy in the core
([D6, purity](00-architecture.md)):

```python
def legal_mask(state: GameState, seat: int) -> list[bool]:                 # len 109
def action_id(action: Action, state: GameState) -> int: ...
def decode_action(aid: int, state: GameState, seat: int) -> Action: ...
```

**Built against `GameState`/`Action`, not `SeatView`/`Intent` — permanently, not a stopgap.**
`mahjong_core` must not depend on `app.views` (layering only runs one way, `app` →
`mahjong_core`), so `legal_mask`/`action_id`/`decode_action` stay `GameState`-based even though
`SeatView` (`app/views.py`) exists now. `docs/04-bots.md §1`'s `Bot.act(view, mask, deadline)`
gets its `mask` from whoever drives the bot calling `legal_mask(state, seat)` against the real
`GameState` it already holds and passing `(view, mask)` to the bot together.

**`action_id` also takes `state`, not just the action.** A `ClaimChow`'s `meld` alone can't say
whether the claimed discard was the run's low/mid/high tile: `Meld.__post_init__` sorts `tiles`
by physical id, which drops which one came from the discard vs. the claimer's own hand once the
`Meld` is built. `state.claim_window.tile` is where that's actually recorded, so encoding a
`ClaimChow` needs it. Every other `Action` variant is self-describing and ignores `state`.

> **Property test:** across every state the self-play harness reaches,
> `action_id(decode_action(aid, state, seat), state) == aid` for every **type-level** legal `aid`
> — both sides of the round trip operate on `tile_type`, never physical `tile_id` (four physical
> 5s collapse to one action id; decoding can't recover which one was meant, because the action
> space was never supposed to know). Also assert every set bit in `legal_mask` decodes to
> something the engine accepts, and the mask is never all-false in an acting phase. **Met** —
> `server/mahjong_core/ml.py`,
> `server/tests/test_ml.py`; states swept from real `RandomBot` self-play games
> (`bots.random`/`engine.reduce`), the same machinery `test_selfplay.py` uses, under `hypothesis`.

The mask comes from the engine, never from the encoder or the network. The heuristic bots use
`legal_mask` too, so a bug in it breaks gameplay immediately instead of poisoning training later.

## 2. Game records

Persisted from M1 for replay and crash-recovery, not (yet) for training — see §3 for why
recording bot-vs-bot games earlier doesn't currently buy anything.

```python
@dataclass(frozen=True)
class GameRecord:
    engine_version: str      # bump on any change to the reducer, wall order, or
                              # flower-replacement ordering
    ruleset: RuleSet         # full body, not a hash — a hash can't be replayed
    seed: int
    actions: list[Action]
    outcome: GameOutcome
```

**Policy:** an `engine_version` bump invalidates replay of every `GameRecord` written under an
older version, and there is no migration path — old records simply stop replaying. Without this
policy stated somewhere, a routine bug fix to the reducer, wall order, or flower-replacement
ordering silently invalidates every stored game and every crash-recovery path, with no way to
detect it after the fact. `ruleset` is the full body rather than `ruleset_hash` for the same
reason: a hash tells you a record doesn't match current rules, but only the full ruleset lets you
actually replay it.

A complete game does not replay from "a few hundred bytes": a 半莊 (four-hand set) runs roughly
600–1,500 actions, and the action log alone is several times that figure in bytes before
considering the ruleset body and outcome. Still cheap to store and cheap to regenerate (pure +
seeded), but size Postgres storage ([05-roadmap §9](05-roadmap.md)) off the real number.

**Implementation note:** the dataclass above isn't materialized separately — the `games` table
row (`server/app/db/models.py`) *is* the persisted `GameRecord`, built by `server/app/db/records.py`'s
`save_game_record(session, state, actions, players=...)` straight from a finished `GameState` (its
`ruleset`/`game_seed`/`seats[*].score`) plus the `Action` log that produced it. `Action` and
`RuleSet` already carry `to_dict`/round-trippable serialization (`RuleSet.to_dict`/`from_dict`,
`actions.action_to_dict`/`action_from_dict`); `outcome` is `mahjong_core.state.GameOutcome`
(`hand_count`, `final_scores`), extracted from a `Phase.GAME_OVER` state by
`mahjong_core.engine.game_outcome`. `engine_version` is `mahjong_core.engine.ENGINE_VERSION`,
stamped by `save_game_record` itself, never caller-supplied. `app/db/records.is_replayable(record)`
implements the policy above as an exact `engine_version` equality check.

## 3. Everything else — deferred, and why

**Recording bot-vs-bot games as training data "from M1 onward"** — an earlier draft's advice —
turned out to be pointless on its own: M1's only bots are `RandomBot`s, the behaviour-cloning
prior has to be `FaanBot` (§4 below), and the engine's own pure-and-seeded property means
regenerating old self-play data whenever it's actually wanted is free. There's nothing to lose by
waiting; §2 above still persists `GameRecord`s from M1, just for replay/crash-recovery, not framed
as training-data collection.

The larger reason to defer the ML project itself, not just the recording: **there is no Hong Kong
equivalent of the Tenhou corpus that Mortal and Suphx trained on.** The only available data source
is self-play against `FaanBot`, and behaviour cloning from a single teacher **caps network
strength at that teacher's own strength** — you need RL on top to exceed it, not just supervised
learning on more self-play games. "Self-play PPO, batched inference serving" is not a casual
day-2 bullet point; Suphx was trained with thousands of GPU-hours. §6 below is the plan that
works around this: the first phase is supervised (exact labels, no teacher cap), and has its own
success metric (§6.5). A compute budget is still undefined for phase 3 (RL) — write it down before
starting that phase, not after.

Deferred — see [99-deferred.md](99-deferred.md). Full list with provenance in
[99-deferred.md](99-deferred.md): the `SeatView` input-boundary writeup, feature-plane encoding,
the PettingZoo AEC wrapper, behaviour cloning from `FaanBot`, self-play PPO, and batched
inference serving. **Shared feature functions (shanten/ukeire/safety as pure functions of a
`SeatView`) are done, not deferred** — `server/bots/features.py`/`safety.py`/`valuation.py`
already export them (`99-deferred.md`'s "Shared feature functions" entry has the full
correction); a day-2 encoder can call them today.

**`server/ml/` now exists (2026-09-26)** as an empty, import-guarded skeleton package
(`__init__.py`, `train.py`, `configs/bc.yaml`) — just enough that the `ml` extra, the
Dockerfile's `ml` stage, and `docker-compose.yml`'s `trainer`/`arena` services, all of which
already pointed at `ml.train`/`ml/configs/bc.yaml`, actually resolve instead of naming a module
that doesn't exist. `python -m ml.train --help` works; a real `--config` run raises
`NotImplementedError` pointing at `99-deferred.md`. Nothing in this section is any less deferred
because of it — no encoding, no AEC wrapper, no training loop.

## 4. Reward under `min_faan`

With `min_faan = 3`, **reward is not correlated with shanten**. A speed-maximising policy reaches
tenpai constantly and is then forbidden from winning, because the fast all-sequences hand is
1 faan.

Published mahjong agents are riichi agents, where riichi is itself a declarable yaku and speed
therefore aligns with reward. That advice does not transfer, and shanten-based reward shaping
will train the wrong policy here.

Consequence: `FaanBot` (value-aware, now built in M4 rather than M6 —
[05-roadmap §2](05-roadmap.md)) is the bot worth investing in, because it's also the
behaviour-cloning prior that bootstraps any future network. Keep
`tenpai_rate_on_sub_minimum_hand` in the arena metrics ([04-bots §8](04-bots.md)) — it's the
canary for this failure mode in both heuristic and learned bots.

## 6. Training plan

### 6.1 Where the gap is

| Fact | Source | Consequence |
| --- | --- | --- |
| `ORACLE` beats `FaanBot` by **+12.1 points/game, 95% CI [10.2, 14.0]** (200 duplicate sets) | [04-bots §10](04-bots.md) | a large, measured headroom exists |
| That gap is almost all defence: deal-in **1.1% vs 15.2%**, win rate 0.20 vs 0.17 | same | the weak link is `tile_risk`'s heuristic `P(deal_in \| tile)`, not offence |
| No HK equivalent of the Tenhou corpus; the only teacher is `FaanBot` | §3 | cloning `FaanBot` caps at `FaanBot` |
| Speed ≠ reward under `min_faan` | §4 | reward is hand point delta, never shanten |
| `SearchBot` (PIMC over `FaanBot` rollouts) was worse than `FaanBot` | [04-bots §6](04-bots.md) | the missing piece is a better evaluator, not more search |

Self-play runs with the full `GameState`, so **"is seat X tenpai, and on which tiles" is an exact,
free label**. The most valuable sub-problem is therefore plain supervised learning — no teacher,
no ceiling, no RL.

### 6.2 Phase 1 — opponent-danger model

- **Input:** a redacted `SeatView` → feature planes. **Built:** `server/ml/encode.py`'s
  `encode_seat_view`/`encode_ruleset` (99-deferred "Feature-plane encoding" has the full shape
  and rationale), covering both the tile planes and the `RuleSet` fields that change correct play
  (`min_faan`, `hand_sets`, `faan_overrides`, `wall_reserve`). Existing `bots/features.py`/
  `safety.py`/`valuation.py` outputs may still ride along as extra channels later — not done yet,
  the encoder above doesn't call them.
- **Heads, per opponent:** `P(tenpai)`, `P(wait on t)` for all 34 `tile_type`s, expected faan if
  dealt into (per tile, not per opponent: `opponent_expected_faan` is `(3, 34)`, an int 3–10 where
  the tile is a legal win, 0 elsewhere).
- **Labels:** from the real `GameState` at each recorded decision — exact, not estimated. **Built:**
  `bots/labels.py`'s `is_tenpai`/`winning_tile_types`/`expected_faan_if_won`/
  `danger_labels_for_opponents` — the exact three label heads below (`P(tenpai)`, `P(wait on t)`,
  expected faan), computed straight from `GameState`/`SeatState`, never through
  `app.views._omniscient_seat_view` (that function stays pinned to its one call site,
  `tests/test_oracle_containment.py`). `bots/arena.py`'s pre-existing tenpai/winning-tile stats
  now call these instead of duplicating them (`04-bots.md` §9's arena `hand_sets` housekeeping
  note is closed as a result).
- **Dataset generation:** **Built, redesigned 2026-09-29 after an architecture review found a real
  shortcut-learning risk in the first version:** `server/ml/generate_dataset.py` — self-play games
  (mirrors `bots/selfplay.py`'s `play_game` stepping logic), one row per real turn decision,
  written as parquet shards plus one `manifest.json` per output directory (ruleset + bot roster,
  written once — constant for the whole run, not repeated per row).

  **What changed and why:**
  - **Seat↔personality assignment is now randomized per game** (`_shuffled_roster`, seeded off
    that game's own seed via an independent `random.Random` instance from the one driving
    in-game claim-arrival order — deterministic and reproducible, not fixed-per-seat-forever).
    The first version pinned one `FaanBot` weight profile to one seat for the *entire* generation
    run — since dealer for hand 1 is always seat 0, `context`'s dealer/seat-wind fields let a
    model trivially read off "this is seat 2 → the defensive bot" instead of learning genuine
    board-state danger signals. The assignment is recorded as `seat_personalities` row metadata
    (never a model input).
  - **Row schema stores raw per-tile-type counts (0–4), not a specific model-input encoding.**
    The first version stored `encode_seat_view`'s already-thermometer-expanded float arrays
    directly, baking one specific encoding choice into the data and inflating both storage (~4×)
    and inter-process pickling cost under `--parallel`. Thermometer expansion (or whatever
    encoding `ml/dataset.py` ends up wanting) is now a training-time choice, revisitable without
    regenerating data. This also means the script no longer depends on `ml.encode` or numpy at
    all — `bots/labels.py`, `bots/features.py`, and `mahjong_core` are pure Python, so only
    pyarrow is needed for the parquet write.
  - **Context fields constant by the row-capture design itself are dropped.** Verified against
    the first (now-discarded) dataset at ~2M rows: the turn-holder is always relative seat 0 and
    phase is always `AWAIT_ACTION` for every row, because rows are only ever captured on the
    acting seat's own turn — not incidentally true, structurally guaranteed by `play_and_label`'s
    `if not is_claim` gate. `prevailing_wind` is kept despite being constant under the single
    `hk_classic` (`EAST_ONLY`) ruleset this run uses, since that constancy is a property of the
    ruleset, not of the capture design, and won't hold once multi-ruleset generation exists.
  - **`opponent_winning_tiles` is now a fixed-width `(3, 34)` multi-hot array**, not a ragged
    list — direct training target, no collate-time padding logic needed. Kept alongside (not
    replaced by) `opponent_expected_faan`: the two together let a consumer distinguish
    "structurally complete but sub-minimum" (docs/04-bots.md §4's canary metric) from "a real,
    legally-declarable win" (`expected_faan > 0`) — training the wait-probability head against
    the wrong one of these was a second review finding, addressed at the model-design stage, not
    here (the data already carries both distinctly).
  - **Schema v3 (2026-09-29).** `ml/raw.py` (`raw_row`) is the one place view-derived columns are
    built, shared with the encoder. v2 leaked other seats' concealed-kong tile types through
    `meld_counts` (`SeatView.melds` is unredacted in-process) and dropped discard order and
    flowers; v3 hides those tile types, and adds `discard_seq` (per seat, tile types oldest first
    — recency is a strong danger signal `bots/safety.py`'s `_tempo_multiplier` already uses),
    `concealed_kongs` and `flowers` (counts). Discard order can't be recovered from v2's
    cumulative `discard_counts`, so v2 data is not trained on. `play_and_label` takes a
    `row_hook(state, seat, row)` for offline baselines that need the live `GameState`.

  Opponent variety (§6.6) is available via `--bots` — any `bots/arena.py` `BOT_REGISTRY` mix,
  including the `FaanBot` weight-profile variants (`FaanBotAggressive`/`FaanBotDefensive`/
  `FaanBotFlushChasing`, see §6.6) — now shuffled per game rather than fixed per seat. No ruleset
  variety yet — one `--ruleset` preset per run.

  `--parallel N` runs games across a `ProcessPoolExecutor`, same pattern as `bots/arena.py`'s own
  `--parallel` — a rolling pool (`_run_parallel`) keeps `N` games in flight and tops up as each
  completes, rather than `bots/arena.py`'s submit-all-then-wait shape, since this generator runs
  unbounded by default and needs to flush shards incrementally. Games finish out of seed order
  under parallelism, so shard filenames use the real min/max seed among that shard's accumulated
  rows, not an assumed-contiguous range; `tests/test_generate_dataset.py` pins that no seed is
  dropped or doubled across shard boundaries.

  **`fork` multiprocessing context, chosen conditionally (`_mp_context`), not the platform
  default.** Measured directly on this workload (120 games, 12 workers, back-to-back in one
  process): the platform default (`forkserver` on this interpreter) managed 0.860 games/sec,
  `fork` managed 1.518 games/sec — a ~1.8× difference at the same worker count. `fork` is only
  safe when the current process is single-threaded at pool-creation time (a thread other than
  main could hold a lock the forked child inherits pre-acquired, forever) — `_mp_context` checks
  `threading.active_count()` at call time and falls back to the platform default otherwise; this
  isn't a hypothetical guard, running the test suite under `fork` unconditionally triggered
  Python's own `DeprecationWarning` for exactly this condition, because pytest's own process is
  multi-threaded.

- **Integration:** replaces `deal_in_probability` inside `bots/safety.py`'s `tile_risk`. The rest
  of `FaanBot`'s decision logic stays untouched — the same move `ORACLE` made (§10 of
  [04-bots](04-bots.md)), with a learned estimate where `ORACLE` has exact knowledge.
- **Model:** small 1-D conv/ResNet over the 34 tile axis, ~1M params, sized for ≤5 ms
  single-sample CPU inference (§7).
- **Baseline:** gradient-boosted trees on the existing hand-built safety features, to confirm the
  net is earning its complexity.

### 6.3 Phase 2 — `FaanBot` weight search (optional)

CMA-ES/Optuna over `_weights_for_turn`'s `w_value`/`w_speed`/`w_safety` against the §8 arena, on
top of phase 1. Fitness is noisy: one CI-meaningful evaluation is ~1,000 duplicate sets, ≈2
core-hours (§7), so a search of ~100 evaluations is a multi-day CPU job. Expect small gains.

### 6.4 Phase 3 — learned policy (T4)

1. **Clone `ORACLE`, not `FaanBot`.** `ORACLE` is measurably stronger, so the cloning ceiling
   moves up. The student sees only the redacted view; this is the imitation-from-privileged-expert
   setup Suphx's oracle guiding addresses, and the student will fall short of the teacher by some
   margin — the goal is to beat `FaanBot`, not to match `ORACLE`.
2. **PPO fine-tune** with a value head. Reward = hand point delta, scaled (limit hands swing
   sharply). KL penalty toward the cloned policy to prevent collapse. Opponent pool per §6.6.
3. Blocked until a compute budget is written down (§7's RL row is why).

Decision trees/GBDT are **not** a candidate policy: tile input is structured (suits, runs, 34
positions), trees can't share weights across tile positions, and a hand-feature GBDT policy is
just a re-derivation of `FaanBot`.

### 6.5 Success metric

| Phase | Merge gate |
| --- | --- |
| 1 | `FaanBot` + learned `tile_risk` vs `FaanBot`: paired-duplicate CI ([04-bots §8](04-bots.md)) excludes zero in the candidate's favour; `tenpai_rate_on_sub_minimum_hand` not worse |
| 1 (offline) | wait-prediction log-loss/AUC beats the heuristic `deal_in_probability` on held-out games, including the held-out opponent type (§6.6) |

### 6.6 Opponent variety

Whether more bot variety helps depends on the phase:

| Phase | Helps? | Why |
| --- | --- | --- |
| 1 | **yes** | labels are exact regardless; variety fixes the *input* distribution. A danger model trained only against `FaanBot` learns `FaanBot`'s discard tells, then reads humans at live tables. |
| 3, cloning | **no — hurts** | several teachers of similar strength give contradictory labels for the same state; the averaged policy can be worse than any of them. Only a *stronger* teacher (`ORACLE`) raises the ceiling. |
| 3, RL | **yes** | an opponent pool (variants + past checkpoints) stops the policy from overfitting to exploiting `FaanBot`. |

**Variants are parameterisations of existing bots, not new hand-written tiers** — a new tier is
~900 lines plus tuning rounds ([04-bots §2](04-bots.md)); a weight vector is free:

- `FaanBot` weight profiles — aggressive / defensive / flush-chasing. **Built:**
  `bots/faanbot.py`'s `WeightProfile` (multipliers on `_weights_for_turn`'s `(w_speed, w_value,
  w_safety, w_flex)`), `BASELINE`/`AGGRESSIVE`/`DEFENSIVE`/`FLUSH_CHASING`; `FaanBot.__init__`
  takes `weight_profile: WeightProfile = BASELINE`, so the default constructor's behaviour is
  provably unchanged (`BASELINE`'s all-1.0 multipliers, and `tests/test_faanbot.py`'s full
  existing suite passes unmodified). Registered in `bots/arena.py`'s `BOT_REGISTRY` as
  `FaanBotAggressive`/`FaanBotDefensive`/`FaanBotFlushChasing`, usable from
  `ml/generate_dataset.py --bots` immediately. `tests/test_faanbot.py` pins one real, verified
  divergence per profile against `BASELINE` (`FaanBot.act` actually run, not just the formula
  argued about). Overlaps with 99-deferred "Bot personas" — one implementation serves both, see
  that entry for what's still not done (name/think-time, not just weights).
- ε-random action mixing, for human-like noise — not built
- `EfficiencyBot` (speed-only, already in `BOT_REGISTRY`), `ORACLE` (near-perfect folding, not in
  `BOT_REGISTRY` — would need a `BotJobTag`/worker-pool-free construction path since `ORACLE`
  normally requires the omniscient view machinery `bots/labels.py` deliberately avoids)
- mixed rulesets (`hk_classic`/`hk_strict`) — requires ruleset-as-input (§6.2); not built,
  `ml/generate_dataset.py` takes one `--ruleset` per run

**Generalisation check:** hold one variant out of training entirely and evaluate phase 1 against
it. A large drop means the model is overfitting to its opponents and needs more variety; no drop
means more variety buys little.

Human game records as training data are deferred — see 99-deferred "Human game records as
training data".

## 7. Compute constraints

Assume training runs on an ordinary multi-core CPU machine with **no CUDA GPU** — plan CPU-only.
Sustained multi-hour runs on laptop-class hardware throttle, so budget in core-hours, not
wall-clock. Memory and disk are not constraints at the dataset sizes below.

Self-play cost per core (order of magnitude, `hk_classic`):

| Setup | Per decision | Per game |
| --- | --- | --- |
| engine + `RandomBot` ×4 | ~0.15 ms | — (random play rarely clears `min_faan`, so games are unrepresentatively long) |
| engine + `FaanBot` ×4 | ~4.6 ms | ~1.6 s, ~350 decisions |

`FaanBot` is ~97% of per-decision cost; the engine is not the bottleneck for data generation.

| Phase | Feasible on CPU? | Cost (derived from the above) |
| --- | --- | --- |
| 1 data | yes | ~2k games ≈ 0.7M labelled decisions per core-hour |
| 1 training | yes | a ~1M-param conv net is an overnight-scale CPU job at 10⁶–10⁷ samples |
| 2 | yes | ~2 core-hours per CI-meaningful evaluation (~1,000 duplicate sets) |
