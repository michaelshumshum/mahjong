# 06 — ML readiness

Training a network is a **day-2 project**. This doc is the short list of things to get right in
M1–M4 so that day 2 isn't a rewrite. Everything below is cheap now and expensive to retrofit.

## 1. Game records

The engine is pure and seeded ([00-architecture §3](00-architecture.md)), so a complete game
replays from a few hundred bytes and re-encoding a stored game is free. **Start recording now** —
every bot-vs-bot game from M1 onward is training data later.

```python
@dataclass(frozen=True)
class GameRecord:
    ruleset_hash: str
    seed: int
    actions: list[Action]
    outcome: GameOutcome
```

## 2. Input boundary

Already the plan in [04-bots §1](04-bots.md); it is also the ML boundary.

```
GameState ──view_for(seat)──► SeatView ──► bot ──► Intent
                                 │
                                 └──► (day 2) encode() ──► tensor ──► policy
```

The encoder takes `SeatView`, never `GameState` — so a network trained this way is structurally
un-cheatable. The rule to hold in M3: **`view_for` is the only path to seat-visible state — no
shortcuts for bots, ever.**

## 3. Action space

Costs about a day now; genuinely hurts to retrofit once bots, replay records, and UI assume a
shape. A fixed, flat, complete discrete space — every legal action maps to exactly one id, and
back:

```
[  0 ..  33]  DISCARD          tile_type t
[ 34 ..  67]  CONCEALED_KONG   tile_type t      (暗槓)
[ 68 .. 101]  ADDED_KONG       tile_type t      (加槓)
        102   PASS                              (decline a claim — and decline a win)
        103   CHOW_LOW         claimed tile is lowest  → use t+1, t+2
        104   CHOW_MIDDLE      claimed tile is middle  → use t-1, t+1
        105   CHOW_HIGH        claimed tile is highest → use t-2, t-1
        106   PUNG
        107   KONG                              (exposed, from a discard)
        108   WIN                               (self-draw or on a discard)
                                                 N_ACTIONS = 109
```

- **Chow is relative** (low/middle/high) — the claimed tile is known from context. Same
  convention as Suphx/Mortal.
- **Kongs are tile-indexed** because you can hold several options at once on your turn.
- **`PASS` covers declining a win**, a real strategic choice under `min_faan`.
- Flower reveal is not an action — it's forced and the engine handles it.

Three pure functions in `mahjong_core`, plus one property test:

```python
def legal_mask(view: SeatView) -> np.ndarray:                 # (109,) bool, engine-produced
def action_id(view: SeatView, intent: Intent) -> int: ...
def decode_action(view: SeatView, aid: int) -> Intent: ...
```

> **Property test (write it in M2):** across every state the self-play harness reaches,
> `decode_action(view, action_id(view, i)) == i` for every legal intent, every set bit in
> `legal_mask` decodes to something the engine accepts, and the mask is never all-false in an
> acting phase.

The mask comes from the engine, never from the encoder or the network. The heuristic bots use
`legal_mask` too, so a bug in it breaks gameplay immediately instead of poisoning training later.

## 4. Shared feature functions

T1/T2 need shanten, ukeire, safe-tile inference and faan-reachability regardless
([04-bots](04-bots.md)). Put them in `mahjong_core` as **pure functions of a `SeatView`**, not
buried inside bot classes; the day-2 encoder calls the same functions.

The encoding itself — feature planes over the 34 tile types, thermometer-encoded counts, players
in relative seat order — is day-2.

## 5. Reward under `min_faan`

With `min_faan = 3`, **reward is not correlated with shanten**. A speed-maximising policy reaches
tenpai constantly and is then forbidden from winning, because the fast all-sequences hand is
1 faan.

Published mahjong agents are riichi agents, where riichi is itself a declarable yaku and speed
therefore aligns with reward. That advice does not transfer, and shanten-based reward shaping
will train the wrong policy here.

Consequence for M1–M6: `FaanBot` (value-aware) is the bot worth investing in, because it's also
the behaviour-cloning prior that bootstraps the network. Keep `tenpai_rate_on_sub_minimum_hand`
in the arena metrics ([04-bots §8](04-bots.md)) — it's the canary for this failure mode in both
heuristic and learned bots.

## 6. Checklist

| When | Do | Cost |
| --- | --- | --- |
| M1 | Persist a `GameRecord` for every game, bot-only included | ~2h |
| M1 | Self-play harness emits `GameRecord`s (it generates them already) | free |
| M2 | `action_id` / `decode_action` / `legal_mask` + round-trip property test | ~1 day |
| M2 | Shanten / ukeire / safety as pure `SeatView` functions in `mahjong_core` | free (needed for bots) |
| M3 | `view_for` is the sole path to seat-visible state, bots included | free |
| M4 | Bot `act()` signature takes `SeatView` + `legal_mask`, returns an action id | ~2h |
| — | **Everything else is day 2** | — |

Day-2 work, explicitly *not* now: feature encoding, reward design,
[PettingZoo AEC](https://pettingzoo.farama.org/api/aec/) env wrapper, behaviour cloning from
`FaanBot`, self-play PPO, batched inference serving. Worth reading when you get there:
[Suphx (arXiv:2003.13590)](https://arxiv.org/abs/2003.13590) for feature planes and oracle
guiding, and [Mortal](https://github.com/Equim-chan/Mortal) for a production open-source encoder
and action space.
